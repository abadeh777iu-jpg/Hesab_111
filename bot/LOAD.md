# آمادگی برای افزایش درخواست‌ها — ظرفیت محدود و قابل‌کنترل

این تغییر برای **تحمل موج درخواست و کنترل فشار** است؛ نه وعدهٔ تعداد نامحدود کاربر، افزایش سهمیهٔ منابع رایگان یا تضمین تحویل. مسیر Cloudflare پیش‌فرض فعال است و binding، migration، حساب، خرید یا سرویس صف تازه‌ای لازم ندارد. از Durable Objects موجود استفاده می‌شود. اجرای محلی Node همچنان مسیر قدیمی خودش را دارد.

## دریافت و پردازش جدا شده‌اند

1. webhook همچنان secret، اندازهٔ بدنه، چت خصوصی، هویت فرستنده، allowlist و ساختار callback را بررسی می‌کند.
2. فقط متن لازم یا callback فشرده، شناسهٔ update و آدرس webhook محاسبه‌شده توسط سرور در صف خصوصی همان کاربر ذخیره می‌شود. پروفایل، فایل‌های ورودی و فیلدهای اضافی تلگرام نگه داشته نمی‌شوند. متن صف حداکثر ۶۰۰۱ کاراکتر است تا ورودی بیش از سقف ۶۰۰۰ در پردازش، بدون فراخوانی مدل، رد شود.
3. پاسخ HTTP موفق بعد از ثبت پایدار پذیرش/رد داده می‌شود، **نه پس از پایان مدل یا دانلود**. کار اصلی با alarm پایدار اجرا می‌شود؛ به عمر `waitUntil` تکیه ندارد. تأیید callback و پیام شلوغی best-effort و با مهلت دو ثانیه‌اند.
4. هر چت در هر لحظه فقط یک کار در حال پردازش دارد؛ نوشتن تاریخچه سریالی است. صف دریافت mutex کوتاه جدا دارد و پشت انتظار شبکهٔ مدل یا فایل قفل نمی‌شود.

### سقف‌های فعلی

| بخش | سقف |
| --- | --- |
| کارهای منتظر هر نفر | ۵، به‌اضافهٔ یک جای اضافه برای فرمان‌های کنترل |
| اعتبار درخواستِ درصف | ۱۰ دقیقه؛ بعد از انقضا پردازش تازه شروع نمی‌شود |
| درخواست پذیرفته‌شدهٔ عادی در کل | ۶۴، شامل منتظر و فعال |
| کل با ذخیرهٔ فرمان‌های کنترل | حداکثر ۸۰ |
| کار فعال در کل | حداکثر ۴ lease هم‌زمان، شامل آب‌وهوای خودکار |
| کار سنگین رسانه‌ای | حداکثر ۱ در همان چهار جایگاه؛ عکس، ویس، ویدئو، شناسایی موسیقی و ارسال انتخاب کانال |
| lease بازیابی پس از خرابی | ۴ دقیقه |
| رسیدهای جلوگیری از تکرار | حداکثر ۲۰۰ شناسه تا ۳۰ دقیقه برای هر چت |
| اتصال webhook در ثبت تازه | ۴؛ ارتقای اتصال موجودِ کم‌تر از چهار، بدون حذف پیام معوق |

این‌ها **سقف پذیرش و هم‌زمانی** هستند، نه تعداد درخواست در ثانیه یا تضمین سرعت. در صورت اشباع، کار پذیرفته‌شده با backoff تصادفی حدود ۳ تا ۳۱ ثانیه دوباره نوبت می‌گیرد؛ فاصله‌های قبلی چهارثانیه‌ای چت و یک‌دقیقه‌ای رسانه نیز حفظ می‌شوند. بررسی خودکار هوا در شلوغی یک تا دو دقیقه به تعویق می‌افتد تا خودش فشار اضافه تولید نکند. تغییر ترجیح/شهر یا فعال‌سازی تازه‌ای انجام نشده است.

صف پر، پذیرش را رد می‌کند؛ پیام روشن «این پیام برای پردازش پذیرفته نشد» حداکثر یک‌بار در ۳۰ ثانیه برای هر چت، در صورت دسترسی به تلگرام، فرستاده می‌شود. update ردشده خودکار دوباره پذیرفته نمی‌شود؛ کاربر باید پیام تازه بفرستد. درخواست پذیرفته‌شده‌ای که منقضی شده، بدون فراخوانی مدل حذف و در صورت امکان با اطلاع کاربر همراه می‌شود. خروج از allowlist باعث حذف بی‌صدای کار منتظر می‌شود. دسترسی عضویت هم هنگام پردازش مجدداً بررسی می‌شود، نه فقط هنگام ورود به صف.

## فرمان‌های کنترل، بازیابی و حریم خصوصی

- `/stop`، `/reset`، `/start`، `/weatherstop`، `/forgetcity` و `/privacy` بر متن عادیِ منتظر مقدم‌اند، اما ترتیب بین فرمان‌های کنترل حفظ می‌شود. جای ذخیرهٔ سراسری، پذیرش آن‌ها را در موج پیام‌های معمولی آسان‌تر می‌کند؛ زمان پاسخ فوری تضمین نمی‌شود.
- `/reset` متن‌های منتظر قبلی را حذف و ticketهای آن‌ها را آزاد می‌کند؛ هنگام اجرا تاریخچه، شهر و دکمه‌های قبلی را پاک و پیام‌های خودکار را خاموش می‌کند. کاری که از قبل شروع شده ممکن است پیش‌تر برای ارائه‌دهنده ارسال شده باشد و قابل پس‌گرفتن نیست.
- `/start` و `/forgetcity` متن‌های عادیِ منتظر قبلی را کنار می‌گذارند، نه فرمان لغوِ قبلاً درصف را. `/stop` و `/weatherstop` درخواست‌های قدیمیِ درصف برای `/followup` و `/alerts` را هم حذف می‌کنند. لغوهای قبلی و سهمیه‌های مصرف همچنان حفظ می‌شوند.
- صف و کار فعال روی storage ذخیره می‌شوند؛ بازسازی شیء باعث ناپدیدشدن صف نمی‌شود. قبل از فراخوانی سرویس، شناسهٔ update در جلسه ثبت می‌شود. بازیابی، update قبلاً ثبت‌شده را دوباره به مدل نمی‌فرستد. خطای گذرای ثبت اولیه، بدون ازبین‌بردن ticket، بعداً بررسی می‌شود.
- **exactly-once نداریم:** خرابی بین ثبت شناسه و فراخوانی/ارسال می‌تواند پاسخ را از دست بدهد. برای جلوگیری از هزینه یا ارسال تکراری، تولید پولی و `sendVideo` کورکورانه تکرار نمی‌شوند. خرابی طولانی زیرساخت یا پایان سهمیهٔ Cloudflare هم تضمین تحویل را از بین می‌برد.
- alarm واحد هر چت، نزدیک‌ترین موعد صف/بازیابی/حذف سابقه/سهمیه/احوال‌پرسی/هوا را نگه می‌دارد؛ زمان‌بندی پاک‌سازی نباید موعد صف را بازنویسی کند. متن در پایان پردازش حذف می‌شود؛ پاک‌سازی کار منقضی و رسیدها با alarm است و تأخیر اجرای زیرساخت ممکن است. دادهٔ منقضی برای شروع کار تازه استفاده نمی‌شود. نسخه‌های پشتیبان تابع Cloudflare‌اند.
- هماهنگ‌کنندهٔ `MARKETS` با نام `bot-capacity` فقط ticket مبهم update/lease و مهلت/نوع را نگه می‌دارد، نه chat ID، متن، فایل، کلید یا آمار کاربران. ticketهای منقضی در درخواست بعدی کنار می‌روند؛ TTL برای اعتبار استفاده است، نه تضمین حذف فیزیکی در همان لحظه. لاگ متن/خطای خام، شمارندهٔ نمایشی یا analytics اضافه نشده است.

## استفادهٔ مجدد از ویدئوی عمومی

بعد از ارسال موفق، حداکثر ده `file_id` معتبر تلگرام برای URL عمومیِ پاک‌شده، تا پنج دقیقه قابل استفاده‌اند. درخواست همان ویدئو از کاربری دیگر می‌تواند با همان شناسه ارسال شود؛ در این حالت دانلود MP4 و آپلود bytes دوباره انجام نمی‌شود. فایل ویدئو در storage برنامه ذخیره نمی‌شود. به تلگرام URL دلخواه کاربر داده نمی‌شود؛ فقط bytes اعتبارسنجی‌شده یا `file_id` بازگشتی خود تلگرام ارسال می‌شود.

هر دریافت همچنان سهمیهٔ شخصی را مصرف می‌کند. cache hit مصرف تازهٔ منبع ویدئو ندارد. خطای ارسالِ cache، شناسه را برای درخواست بعدی کنار می‌گذارد، اما همان ارسال کورکورانه دوباره انجام نمی‌شود. metadata عمومی منقضی، استفاده نمی‌شود و در نوشتن بعدی کنار می‌رود؛ cache عمومی با `/reset` یک نفر پاک نمی‌شود. نگهداری فایل اصلی در تلگرام تابع سیاست تلگرام است.

## سهمیه و هزینه همچنان واقعی‌اند

هیچ سهمیهٔ شخصی/مشترکِ تصویر، ویس، Navasan یا اینستاگرام افزایش نیافته و هیچ کلید، provider، fallback پولی یا اشتراک جدیدی اضافه نشده است. برای اینستاگرام همچنان هر نفر روزی پنج تلاش در هر بخش، و کل ربات روزی **ده تلاش تازهٔ منبع در هر بخش** با فاصلهٔ حداقل یک دقیقه بین cache missها دارد. صف، این منبع داوطلبانه را نامحدود نمی‌کند. [جزئیات اینستاگرام](INSTAGRAM.md).

پردازش چت، خبر و متن هوای AI همچنان از اعتبار OpenRouter مدیر مصرف می‌کند. SQLite/alarms/requests کلودفلر هم تابع سقف پلن موجودند. این تغییر مصرف پولی را رایگان نمی‌کند و تست‌ها سقف ترافیک واقعی حساب را ثابت نمی‌کنند. قبل از تبلیغ گسترده، ظرفیت و مصرف حساب و دسترسی منابع را بررسی کنید؛ هیچ خرید یا ارتقای خودکاری انجام نمی‌شود.

## بررسی توسعه و انتشار

```sh
npm run test:bot
npm run bot:cf:check
npm run typecheck
```

آزمون موج ۲۰۰ درخواست ساختگی، تکرار هم‌زمان، پرشدن صف، lease چهار/یک، انقضا، بازیابی، لغو و خرابی موقت storage/capacity را پوشش می‌دهند. تست واقعی workerd با storage/alarm و DO RPC، دریافت پیام و callback جدید هنگام منتظربودن مدل را بررسی می‌کند؛ منابع شبکه همگی ساختگی‌اند و اعتبار واقعی مصرف نمی‌شود. تست workerd اینستاگرام ارسال bytes و استفادهٔ مجدد از `file_id` برای نفر دوم را بررسی می‌کند. این‌ها benchmark ترافیک زنده یا اثبات انتشار نیستند.

مسیر پیش‌فرض وقتی `BOT_ASYNC_UPDATES` تنظیم نشده فعال است. مقدار `false` برای تست سازگاری مسیر قدیمی است و نباید برای بار زیاد تنظیم شود؛ کارهای پایدارِ قبلاً پذیرفته‌شده حتی در آن حالت هم تخلیه می‌شوند. به تغییر Secrets فعلی نیاز نیست. بعد از انتشار، ثبت تازه webhook چهار اتصال می‌گیرد؛ در نصب موجود، همان آدرس تأییدشده هنگام آماده‌سازی دکمه‌ها به حداقل چهار اتصال ارتقا می‌یابد و secret، تنظیم همهٔ updateها و pending updates حفظ می‌شود. URL نامرتبط تغییر نمی‌کند.

کتابخانهٔ [پست‌های کانال](CHANNEL.md) نیز از همین صف خصوصی و lease رسانه استفاده می‌کند؛ ورود پست جدید فقط ثبت metadata عمومی و محدود در شیء مستقل است و هیچ پردازش پولی یا ارسال خودکاری به مخاطبان راه نمی‌اندازد.
